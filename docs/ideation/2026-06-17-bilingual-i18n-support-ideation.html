Ideation: Bilingual i18n Support

判断当前 3D editor 是否值得做中英文国际化，以及最强的切入方向是什么。结论：值得做，但应该先做 message contract 和宿主接入边界，避免把具体 i18n runtime 过早塞进 core。

date: 2026-06-17 topic: bilingual-i18n-support focus: 中英文国际化支持 mode: repo-grounded

Grounding Context

Codebase Context

当前仓库是 pnpm TypeScript workspace：core editor state、commands、validation、runtime projection 和 Workbench model 在 packages/core，React/Vue 适配器在 packages/react 和 packages/vue。README 明确强调 durable state 只能存 versioned scene snapshot 和 .ek3d JSON；Three.js runtime、resolver output、helper state 等不能序列化。

检索没有发现已有 i18n 系统；translate 命中主要是 transform mode，不是翻译能力。反而能看到大量英文文案已经进入 public-ish model 和 UI：InspectorFieldDescriptor.label、InspectorSection.title、InspectorCommandProblem.message 是 core 类型的一部分；material/environment/workbench builders 直接产出英文 label、title、reason、message；React/Vue Workbench 组件也有大量硬编码英文按钮、aria label、placeholder 和状态文本。

典型证据包括：packages/core/src/inspector/types.ts:17 定义字段 label，packages/core/src/inspector/material.ts:33 返回 title: "Material" 和 material field labels，packages/core/src/inspector/environment.ts:41 返回 environment action/field labels，packages/core/src/workbench/workbench-model.ts:526 产出 Ready/Partial/problems 状态文本，packages/react/src/components/WorkbenchToolbar.tsx:69 和 packages/react/src/components/WorkbenchLeftPanel.tsx:151 硬编码默认 Workbench 文案。Vue 侧基本镜像这些字符串。

External Context

外部资料只用于校准边界，不作为选型承诺。i18next 官方文档强调 interpolation、plural、TypeScript 支持和类型安全翻译；react-i18next 的官方入口是 useTranslation hook / provider；Vue I18n 支持 Vue 3 Composition API，且需要关心 legacy/composition 模式；MDN 的 Intl 文档确认数字、日期和语言敏感格式化已有浏览器标准能力。这个外部形态支持“core 不绑定 runtime，adapter/host 可以接入自己 i18n 栈”的判断。

1

Core Message Descriptor Layer Before Any Framework Runtime

Axis: Message boundary and durable state Confidence: 94% Complexity: High

Description: 先把 core/workbench/inspector 产出的 display string 从“直接英文字符串”升级为可翻译 message descriptor：稳定 key、默认英文 fallback、参数 values、必要时的 semantic kind。UI 层可以立刻渲染 fallback，也可以用 translator 把 descriptor 转成中文。这个方向不要求马上引入 i18next、react-i18next 或 Vue I18n。

Basis: direct: packages/core/src/inspector/types.ts:17 exposes label, packages/core/src/inspector/types.ts:51 exposes section title/reason, and packages/core/src/workbench/workbench-model.ts:526 already produces English status labels from core. These strings sit below React/Vue, so adapter-only translation cannot cover the surface cleanly.

Rationale: 这是最重要的地基。它让 core 继续 framework-neutral，同时阻止英文文案继续固化到 public model。后续中英文、宿主自定义翻译、测试和 docs 都可以围绕同一 message key contract 展开。

Downsides: 需要触及 inspector/workbench/problem 类型，会带来 API 设计成本。必须避免把所有用户自定义数据也“key 化”；node name、asset label、scene name 仍然应该是用户内容。

2

Built-in en / zh-CN Workbench Dictionaries Shared by React and Vue

Axis: Default Workbench UI Confidence: 91% Complexity: Medium

Description: 为 install-ready 默认 Workbench 提供内置英文和简体中文词典，覆盖 toolbar、left panel、status bar、inspector chrome、aria label、placeholder、empty state 和 import/recovery UI。React 和 Vue 应消费同一份 key/dictionary contract，而不是各自维护一套翻译。

Basis: direct: packages/react/src/components/WorkbenchToolbar.tsx:69 到 :220 是密集英文按钮和 title，packages/react/src/components/WorkbenchLeftPanel.tsx:151 起也有 Hierarchy、Assets、Import assets、Search assets、Status、Sort 等文案；Vue 左面板和 toolbar 基本复制同一 UI surface。

Rationale: 这个项目已经把 React/Vue default Workbench 当作 npm 包产品化卖点。中英文支持如果只覆盖 core descriptors，不覆盖 default shell，用户第一眼仍会看到英文界面。共享词典还能降低 React/Vue parity 风险。

Downsides: 翻译会暴露中文长文本导致布局溢出的风险，尤其是 toolbar 小按钮和 status bar。实现时需要 browser screenshot 或 DOM 文本 fitting 验证，不能只跑 unit test。

3

Localize Problems and Diagnostics by Code, Not by Serialized Message

Axis: Problems and diagnostics Confidence: 90% Complexity: High

Description: 把 runtime/project/import/material/environment/light problem 的用户展示文案按 problem code 和参数进行本地化。持久或派生 problem 仍保留 code、target、metadata 和 fallback message；UI 渲染时根据 locale 生成 title/detail/actionLabel。不要把中文/英文结果写进 snapshot 或 .ek3d。

Basis: direct: packages/core/src/problems/types.ts defines Problem.code, target, message, and optional display; packages/core/src/assets/import-pipeline.ts creates decoder and extension diagnostics with English display.title/actionLabel; README.md states runtime diagnostics are exposed as problems instead of being written back into snapshot.

Rationale: Problems 是真实用户最需要看懂的地方，也是最容易把英文错误泄漏给中文用户的地方。按 code 本地化还能让宿主覆盖业务术语，同时保留 fallback message 便于调试。

Downsides: 不是所有 Error.message 都能稳定翻译；loader/raw exception 仍可能只能作为 fallback detail。需要区分用户可操作诊断和开发者调试细节。

4

Host Translator Bridge Instead of Owning the User's i18n Runtime

Axis: Host integration surface Confidence: 87% Complexity: Medium

Description: 对 React/Vue/default Workbench 暴露一个小而稳定的 translator bridge，例如 locale、messages、translate(descriptor) 或 i18n prop/composable 参数。默认用内置词典；宿主可桥接到 i18next、react-i18next、Vue I18n 或自己的企业翻译系统。

Basis: external: react-i18next 官方推荐通过 useTranslation 获取翻译函数，Vue I18n 官方支持 Composition API 的 useI18n；二者框架形态不同。reasoned: 该项目同时发布 React、Vue 和 core 包，如果 core 或 shared workbench 绑定其中任一 runtime，会破坏 adapter thin 和 framework-neutral 边界。

Rationale: 宿主应用很可能已经有自己的语言切换、namespace、加载策略和术语表。桥接而不是拥有 runtime，可以让默认 Workbench 立即可用，又不干扰宿主架构。

Downsides: Bridge 设计太宽会变成另一个 i18n 框架；太窄又覆盖不了 plural/interpolation。第一版应只支持本项目需要的 keys、values、fallback 和 basic formatting。

5

Locale-Sensitive Formatting Helpers for Counts, Numbers, and Status Text

Axis: Message boundary and durable state Confidence: 82% Complexity: Medium

Description: 把 selection count、problem count、asset refs、FOV/rotation/position display、status labels、date/time 等显示格式从字符串拼接升级成 locale-aware formatting。优先使用浏览器标准 Intl.NumberFormat/Intl.DateTimeFormat，再由 message descriptor 插入格式化结果。

Basis: direct: packages/core/src/workbench/workbench-model.ts:541 返回 none / ${count} nodes，:526 返回 ${problemCount} problems；React/Vue asset panels 拼接 refs、problems、status 等。external: MDN 文档说明 Intl.NumberFormat 和 Intl.DateTimeFormat 是语言敏感格式化 API。

Rationale: 只翻译固定词不够。中文不需要英文复数，英文需要 plural，数字和日期也应跟随 locale。这个方向能把最常见的“半翻译”问题提前解决。

Downsides: 本项目目前多数数字是编辑器参数而非业务日期，过早做复杂单位系统会超范围。第一版只做 count/status/date/number 的基础格式化，不做完整 unit conversion。

6

Bilingual Verification Harness and String Audit

Axis: Verification and documentation Confidence: 86% Complexity: Medium

Description: 给 i18n 加一个持续防回归层：string audit 测试列出 core/React/Vue 默认 UI 中未 key 化的英文文案；React/Vue Workbench test 分别以 en 和 zh-CN 渲染关键路径；browser screenshot 或 DOM 尺寸检查覆盖中文长文本不溢出；docs 给出宿主如何接入内置词典和自定义 translator。

Basis: direct: 仓库已有 React/Vue Workbench tests、browser tests 和 release verification；AGENTS.md 要求 UI 相关变化用 pnpm test，browser/runtime 行为用 pnpm test:browser。reasoned: i18n 最常见失败不是初次翻译，而是新功能重新硬编码英文或中文布局破裂。

Rationale: 国际化如果没有验证，很快会变成一次性翻译。这个方向让 i18n 成为 package quality gate，尤其适合当前双适配器、默认 Workbench、npm 发布的产品形态。

Downsides: string audit 可能误报技术名词、asset/user-authored labels、test fixture names。需要白名单和清楚规则，不要把测试变成维护负担。

Rejection Summary

# Idea Reason Rejected
1Add i18next directly to coreCore 是 framework-neutral contract；强绑一个 runtime 会增加依赖和 public API 压力。
2Add react-i18next and Vue I18n immediately没有 message contract 前，双 runtime 只会让 React/Vue 各自补洞，无法覆盖 core 产出的英文。
3Translate durable scene/node/asset names这些是用户内容，不是 UI chrome；自动翻译会污染 durable authoring data。
4Store locale in SceneSnapshotLocale 是宿主/session UI state，不是场景真相；写入 snapshot 会违反项目 durable-state 边界。
5Browser-language auto-detection only嵌入式编辑器需要宿主显式控制语言；自动检测可作为默认，但不能是唯一机制。
6Chinese as the only/default UI项目准备发布 npm 包，英文仍是生态默认；正确目标是内置 en + zh-CN 并允许宿主选择。
7Extract every string into JSON in one sweep会机械搬运字符串但不解决 message boundary、参数、problem code 和 host bridge。
8Problem messages only有价值但范围过窄；默认 Workbench 的 toolbar/sidebar/inspector 仍会保持英文。
9Toolbar/sidebar only能快速显效，但 core inspector/problem model 仍泄漏英文，后续返工大。
10Full translation-key codegen first可能有用，但在 key shape 尚未稳定前过早；先用手写 typed key union 或 const dictionary 更务实。
11Machine translation workflow当前需求是中英文产品支持，不是翻译运营系统；可后置到文案规模变大后。
12Persist user language in .ek3d同 snapshot locale 问题；项目包应保存场景和资产 payload，不保存某个宿主 UI 偏好。
13Defer all i18n until 1.0英文已经进入默认 Workbench 和 public model；越晚抽离，API 和测试返工越大。
14Use CSS-only language switching无法处理参数、plural、diagnostics 和 host integration，属于演示层技巧。
